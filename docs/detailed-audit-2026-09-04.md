# Повторный функциональный аудит и проверка безопасности

Дата: 2026-09-04. Проверяемая база: `4cf8176c111ac922ba2c5e14ccc589a8b7969117`.

Это исторический отчёт до исправлений. Последующий выпуск описан в `docs/reliability-release-2026-09-04.md`. Диагностические воспроизведения преобразованы в `tests/audit-regression.test.mjs` и `tests/integrity-database.test.mjs` с проверками правильного поведения.

## Итог

Штатные сценарии интерфейса проходят, но готовность к массовому приглашению клиентов не подтверждена. Обнаружены воспроизводимые риски потери данных, смешивания профилей на одном устройстве и неполной обработки платежей при сбоях базы. Предыдущие успешные проверки этих сценариев не покрывали.

В этой сессии код продукта и production не изменялись. Добавлен диагностический стенд, исправлено ожидание навигации в браузерном тесте и составлен этот отчёт. Ниже перечислены дефекты, а не выполненные исправления.

## Метод и границы

- Проверены исходники frontend, Supabase Functions, миграций и Python-помощника.
- Браузерные тесты запускаются на локальной текущей версии с тестовыми данными. Они не доказывают успешность реальных платежей, доставки Telegram-сообщений или записи в рабочую БД.
- Семь дефектов воспроизведены исполнением реальных JS/TS-функций с управляемыми сетевыми/DB-заглушками. Это не интеграционные тесты Postgres: блокировки, ограничения и RLS реальной БД здесь не моделируются полностью.
- Production проверялся безопасными запросами без авторизации и одним синтетическим подписанным запросом к помощнику на VPS. Записи клиентов, покупки, возвраты и выплаты не создавались.
- Нельзя утверждать отсутствие всех уязвимостей по результатам такого аудита.

## Приоритетные дефекты

### 1. P1: Очередь аналитики смешивается между аккаунтами

Источники: `account-storage.js`, `analytics.js` (`buildEvent`, `flush`); воспроизведение №6.

Профиль и дневник разделены по аккаунтам, очередь `babymode_analytics_queue` — нет. Она содержит имя и дату рождения ребёнка. Неотправленные события аккаунта A после переключения уходят с авторизацией аккаунта B. Сервер связывает эти сведения с B и может записать их в его профиль.

Это подтверждённый риск приватности и целостности на общем устройстве, а не доказательство произвольного удалённого чтения чужих данных. Ранее внедрённая изоляция аккаунтов оказалась неполной.

Исправление: привязать очередь и отправку к владельцу, исключить передачу очереди между аккаунтами, минимизировать личные сведения в аналитике. Отдельно проверить смену аккаунта при запросе в полёте.

### 2. P1: Обычная аналитика перезаписывает основной профиль ребёнка

Источник: `supabase/functions/analytics-events/index.ts:72–105`; воспроизведение №1.

Даже `app_open` делает безусловный `upsert` в `babies`. Устаревший клиент может заменить сведения, только что сохранённые через бот. Отсутствующий возраст преобразуется через `Number(null)` в ноль, а отсутствующие имя и дата — в `null`. Защиты по версии профиля нет.

Это возможная причина повторного заполнения ребёнка и откатов данных. Не установлено, что именно этот путь вызвал конкретный прошлый случай пользователя.

Исправление: аналитика не должна записывать канонический профиль. Оставить явные операции сохранения через синхронизацию и бот с проверкой версии.

### 3. P1: При частичном сбое оплаты теряется партнёрская комиссия

Источник: `supabase/functions/_shared/yookassa.ts:122–208`; воспроизведение №2.

Сначала платёж становится `paid`, затем записываются соглашение и подписка. Если запись подписки падает, повторный вызов восстанавливает Premium, но `newlyPaid` уже false и начисление комиссии пропускается. Положительный контроль подтверждает: та же оплата подходит для начисления, если вызвать его отдельно.

Кроме того, ряд ошибок внутри `accruePartnerCommission` возвращается как `null`, а не как ошибка для повторной обработки.

Исправление: транзакционная обработка либо восстанавливаемые независимые идемпотентные шаги. Начисление не должно зависеть только от первого перехода статуса оплаты. Нужна сверка уже оплаченных платежей без комиссии.

### 4. P1: Возврат считается обработанным при неуспешном отзыве Premium

Источник: `supabase/functions/yookassa-webhook/index.ts:117–153`; воспроизведение №3.

Ошибки некоторых обновлений БД не проверяются. При отказе обновления `subscriptions` событие возврата всё равно отмечается `processed`. Повторное уведомление уже не восстанавливает пропущенный шаг.

Штатный реальный возврат был проверен пользователем ранее; найденный дефект касается сбоя промежуточной записи, а не каждого возврата.

Исправление: проверять каждый результат, завершать событие только после обязательных изменений и обеспечить безопасное повторение всей обработки.

### 5. P1: Одновременная синхронизация может заменить новые записи старыми

Источник: `supabase/functions/sync-data/index.ts:70–119`; воспроизведение №4.

Чтение версии и последующий `upsert` — отдельные операции. Между ними второй клиент может записать более новую версию; задержанный первый запрос затем заменяет её старой. Управляемое чередование запросов воспроизводит этот исход. Аналогичный подход используется для профиля и настроек.

Исправление: сравнение версии должно выполняться атомарно на стороне БД. Отдельно определить конфликтную политику для разных событий одного дня: даже корректный выбор последней версии дня не объединяет независимые правки автоматически.

### 6. P1: Старые локальные записи без времени изменения исчезают при первом pull

Источник: `cloud-sync.js:90–97`; воспроизведение №5.

Отсутствующий `_updatedAt` превращается в ноль и сравнивается с нулём отсутствующего tombstone. Условие `0 <= 0` отбрасывает запись, хотя её никто не удалял. Начальный pull может выполнить это раньше, чем push присвоит записям время изменения.

Исправление: нормализовать старые данные до слияния, учитывать удаление только при существующем tombstone и сохранить резервную копию до миграции. Не переписывать исторические записи пользователей автоматически без проверенного восстановления.

### 7. P2: Очередь теряет новые события и большие пакеты

Источник: `analytics.js:94`, `supabase/functions/analytics-events/index.ts:37`; воспроизведение №7 и анализ ограничения пакета.

Успешный `flush` очищает всю очередь, включая события, добавленные во время запроса. Клиент также может отправить до 200 событий, сервер обрабатывает первые 20, а клиент после успешного HTTP-ответа удаляет остальные. Потеряться может не только статистика: через этот же канал передаётся отключение уведомлений.

Исправление: ограниченные пакеты с идентификаторами и удалением только подтверждённых событий. Критические настройки вынести из очереди аналитики в подтверждаемые операции.

## Дополнительные замечания

### Напоминания: выключение в боте не отменяет уже поставленные задания

По коду `telegram-webhook/index.ts:143–174` меняется `notification_settings`, но нет отмены ожидающих `schedule_reminders`. SQL `claim_due_schedule_reminders` в `20260730010000_launch_hardening.sql:55` выбирает задания без проверки текущего согласия. Это путь отправки уже запланированного сообщения после отказа пользователя. На живой БД и реальной доставкой не проверялось.

Обычные сообщения боту также записывают `Europe/Moscow` вместо сохранения часового пояса. Настройки бота и `user_app_settings` синхронизации хранятся раздельно. Серверный обработчик `schedule_reminders_planned` не проверяет право на Premium: клиентскую проверку можно обойти собственным авторизованным запросом.

Нужно единое состояние согласия и часового пояса, отмена очереди при отключении и повторная проверка согласия непосредственно перед отправкой. Право на платную функцию проверять на сервере.

### Помощник: ответ доступен, работа модели не подтверждена

Один синтетический подписанный запрос к `/v1/answer` на VPS вернул HTTP 200, `ok:true`, 471 символ за 4,8 с, но `mode:knowledge`. Это резервный ответ базы знаний, не генерация языковой модели. По этому запросу нельзя установить постоянный отказ провайдера или его причину. Полный путь Telegram/веб → квоты → агент → модель и анализ дневника пользователя в этой сессии не проверялся.

### Защитные заголовки сайта

GitHub Pages возвращает HSTS, но в проверенном ответе нет HTTP `Content-Security-Policy` и `X-Content-Type-Options`. Meta-CSP не заменяет все возможности заголовка, включая `frame-ancestors`. Нужна отдельная задача по заголовкам/CSP и проверке совместимости с Telegram; это не основание молча переносить хостинг в рамках аудита.

## Что прошло

- Обычный набор Node-тестов: успешное завершение, 34 результата.
- Python-помощник: 14/14 тестов, включая HMAC, ограничение провайдера loopback, фильтрацию небезопасных ответов и обезличивание контекста.
- Browser smoke: запись и завершение сна, сохранение после перезагрузки, профиль, четыре основных экрана на четырёх размерах, увеличенный текст, доступность последнего действия над нижней навигацией, экраны тарифов/партнёрки/знаний/ритуала, переключение аккаунта и выход. Необработанных JS-ошибок нет. Это не проверка каждого возможного overlay и сочетания данных.
- На production девять защищённых endpoints отклонили запросы без авторизации (401); поддельные Telegram-данные для синхронизации — 401; посторонний Origin — 403; приложение — 200.
- `baby-agent` и `baby-hermes-proxy` активны и запущены не от root, с `NoNewPrivileges`, `PrivateTmp` и `ProtectSystem=strict`. `ProtectHome` соответственно yes/read-only.
- В текущих отслеживаемых JS/TS/HTML/MD/SQL-файлах не найдены совпадения с проверенными форматами OpenAI project key, Supabase PAT и Telegram bot token. Это ограниченный поиск, не гарантия отсутствия всех секретов.

## Что не подтверждено

- Актуальное состояние production RLS, всех миграций, Security Advisor и журналов cron в Supabase.
- Новые реальные оплаты/возвраты YooKassa, Stars, начисления/выплаты партнёрам и доставка поздравлений.
- Устойчивость при одновременной работе 100 клиентов, восстановление БД из резервной копии и внешний пентест.
- Старый отозванный токен остаётся известным историческим риском Git; история в этой сессии не переписывалась. Ранее опубликованные секреты не следует возвращать в использование.

## Как повторить

Из корня `baby-tma`, используя установленный Node с поддержкой `stripTypeScriptTypes`:

```sh
node --test --test-reporter=dot tests/*.test.js tests/*.test.mjs
node --test tests/audit-regression.test.mjs tests/integrity-database.test.mjs
node tests/production-smoke.cjs
node tests/browser-smoke.cjs
```

Для browser smoke нужен локальный сервер на `127.0.0.1:8765`, Playwright и Chrome. Диагностический файл намеренно не включён в glob обычных тестов: его assertions подтверждают существование дефектов, а не правильность продукта. После исправления эти сценарии нужно преобразовать в регрессионные проверки ожидаемого безопасного поведения.

## Рекомендуемый порядок исправлений

1. Убрать запись профиля из аналитики, изолировать очередь, сохранить старые записи при слиянии.
2. Сделать запись версий атомарной и добавить тесты с реальным Postgres.
3. Исправить восстановление оплаты, возврата и комиссии после каждого промежуточного сбоя.
4. Объединить согласие/настройки уведомлений и проверить отключение с уже поставленными заданиями.
5. Восстановить и проверить модельный ответ помощника, затем пройти интеграционные сценарии на отдельных тестовых аккаунтах и актуальную проверку БД.

До выполнения этих пунктов формулировка «всё работает и безопасно» не соответствует результатам проверки.
